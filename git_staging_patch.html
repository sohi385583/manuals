日常の開発において、「とりあえず git add . して全部コミットする」運用だけでは、不要な設定ファイルやログの誤混入、巨大すぎるコミットによるコードレビューの難航、共同開発でのコンフリクトなどの問題に直面します。

本マニュアルでは、Gitの最大の特徴である「ステージング領域（インデックス）」の本質的な活用法、.gitignore による安全な除外設計、そしてコード差分を柔軟に共有・適用できるパッチファイル（.patch）運用を詳しく解説します。

1. 3つの領域とステージングの仕組み

Gitは、ファイルを3つの異なるツリー（領域）で行き来させながら履歴を管理しています。

領域 1

作業ツリー (Working Tree)

エディタで実際に編集しているローカルのファイル群

領域 2: 中間バッファ

ステージング (Index)

git add で選別された「次のコミットに入る変更」

領域 3

リポジトリ (HEAD)

git commit で確定した永続的なコミット履歴

なぜステージング領域が存在するのか？

  • コミットの粒度を整える: 1日の中で複数の修正を行った場合でも、ファイルごと・行ごとにコミットを小分けにできます。
  • 誤コミットの防止: 開発中の実験的コードや、APIキー・認証情報が入ったローカル設定（.envなど）がコミットに混入するのを防ぎます。
  • 変更のプレビュー: 「いまコミットしようとしている差分」だけを git diff --staged で厳密に検証できます。

ショートステータスで状態を一目で把握 (git status -s)

git status -s（または --short）を実行すると、各ファイルのステージ状態が2文字のプレフィックスでコンパクトに表示されます。

$ git status -s
M  src/index.js       # [左文字: M] ステージング済み（コミット対象）
 M src/utils.js       # [右文字: M] 作業ツリーで変更されたが未ステージ
MM src/app.js         # ステージング後、さらに作業ツリーで変更が加わった
A  docs/readme.md     # 新規作成され、ステージング済み
?? test/temp.txt      # 未追跡 (Untracked)
表記 左文字（ステージング状態） 右文字（作業ツリー状態） 意味
?? 未追跡 未追跡 Gitでまだ一度も管理されていない新規ファイル
A 追加済み (Added) 変更なし 新規追加され、ステージング完了している
M 変更済み (Modified) 変更なし 変更がステージング済み（コミット可能）
M 変更なし 変更済み ファイルが編集されたが、まだステージングされていない
MM 変更済み 変更済み ステージした後に、さらにファイルが編集された状態
D 削除済み (Deleted) 変更なし ファイルの削除がステージング済み

2. .gitignore の設定と除外管理

.gitignore は、Gitに「このファイルやフォルダは追跡しないでください」と指示する設定ファイルです。プロジェクトのルートディレクトリに配置します。

パターンの書き方ルール

  • # で始まる行はコメントとして無視されます。
  • / で始まるパスは、.gitignore ファイルがあるディレクトリからの相対パスを示します。
  • 末尾の / はディレクトリ（フォルダ全体）を指定します。
  • 先頭の ! は、それまでの除外ルールを反転（除外から除外＝追跡対象に戻す）します。
  • ワイルドカード（* は任意の文字列、** は任意のディレクトリ階層）が使えます。

代表的な .gitignore テンプレート例

# OS固有の一時ファイル
.DS_Store
Thumbs.db

# ログファイル
*.log
npm-debug.log*
yarn-debug.log*

# 依存パッケージディレクトリ
node_modules/
vendor/

# ビルド成果物・キャッシュ
dist/
build/
.cache/
*.pyc
__pycache__/

# 環境変数・認証情報（絶対にコミットしてはいけないファイル）
.env
.env.local
.env.*.local
*.pem
secrets.json

# エディタ・IDEの作業設定
.idea/
.vscode/settings.json
*.swp

重要（頻出トラブル）: すでに追跡・コミット済みのファイルは .gitignore に書いても無視されない
.gitignore が効果を発揮するのは未追跡 (Untracked) のファイルのみです。すでに過去のコミットに含まれているファイルは、追跡キャッシュをクリアする必要があります。

キャッシュをクリアして .gitignore を反映させる手順

# 1. 特定のファイルだけ追跡を解除したい場合（作業ツリーの実ファイルは消えません）
git rm --cached path/to/.env

# 2. リポジトリ全体で .gitignore を再評価して追跡対象をリフレッシュする場合
# （全ファイルのキャッシュを一旦外し、.gitignore に従い再追加する）
git rm -r --cached .
git add .
git commit -m "chore: .gitignoreを適用し追跡対象から不要ファイルを除外"

グローバルな除外設定 (すべてのリポジトリに適用)

macOSの .DS_Store や個人のエディタ設定など、すべてのリポジトリで共通して除外したいファイルは、グローバル設定を作成しておくと便利です。

# グローバルignoreファイルのパスを指定
git config --global core.excludesfile ~/.gitignore_global

# ~/.gitignore_global に .DS_Store などを記述

3. 部分ステージング (git add -p) と取り消し

1つのファイル内で「バグ修正」と「新機能の実装」を同時に進めてしまった場合、ファイルごとコミットすると履歴が混ざってしまいます。git add -p を使うことで、変更の塊（ハンク / hunk）単位で選択的にステージングできます。

部分ステージングを実行する

git add -p
# または特定のファイルだけを対話形式でステージ
git add -p src/main.js

コマンドを実行すると、変更箇所が1塊（hunk）ずつ表示され、末尾に次のようなプロンプトが現れます：

Stage this hunk [y,n,q,a,d,s,e,?]?
キー 名称 動作
y yes 表示されているハンクをステージングする
n no 表示されているハンクをステージングしない（スキップ）
s split ハンクが大きすぎる場合、さらに細かく分割する
e edit エディタを開き、行単位で手動編集してステージする内容を決める
q quit 途中で対話モードを終了する（決定済みのステージ内容は維持される）
d do not stage このファイルのこれ以降のハンクをすべてステージしない
? help 利用可能なすべてのキーの説明を表示する

ステージングの安全な解除 (git restore --staged)

誤って git add してしまったファイルを、作業中の編集内容はそのままに、ステージング領域からだけ降ろします。

# 特定のファイルのステージングを解除（作業ツリーの変更はそのまま残る）
git restore --staged src/index.js

# すべてのステージングを一括で解除
git restore --staged .

# ハンク単位で対話的にステージングを解除
git restore --staged -p src/index.js

4. 差分確認テクニック (git diff)

コミット前に「どこが変更されたか」を正確に把握することは、意図しないバグ混入を防ぐ最重要ステップです。Gitには比較対象に応じた3通りの diff コマンドがあります。

コマンド 比較対象 使いどころ
git diff 作業ツリー vs ステージング まだ git add していない編集内容を確認する
git diff --staged
(または --cached)		 ステージング vs HEAD (直前コミット) 次の git commit で実際に記録される内容を最終確認する
git diff HEAD 作業ツリー ＋ ステージング vs HEAD 直前のコミットから現在までに変更されたすべての内容を見る

よく使う diff オプション

# 変更のあったファイル名と変更行数のサマリーだけを表示
git diff --stat

# 単語単位での差分ハイライト（インライン変更を見やすくする）
git diff --word-diff

# 空白文字・改行コードの違いを無視して差分を表示
git diff -w

5. パッチファイルの作成と適用 (.patch / git apply)

パッチ（Patch）とは、Gitの差分情報をプレーンテキスト形式で保存したファイル（通常 .patch や .diff 拡張子）です。

パッチが活躍する場面:
• リモートリポジトリ（GitHubなど）へのプッシュ権限がない環境で、コード差分をメールやチャットで共有する
• AIエージェントが作成した修正差分をローカル環境でレビュー・適用する
• 本番サーバーに緊急ホットフィックスを適用する
• ブランチを切り替えずに、別の環境へ変更内容を一時的に移送する

1. パッチファイルを作成する

A. 作業中の未ステージ差分をパッチにする

# 作業ツリーの未ステージ差分を patch ファイルに出力
git diff > my_feature.patch

# 特定のファイルだけの差分をパッチにする
git diff path/to/file.js > file_fix.patch

B. ステージング済みの差分をパッチにする

# git add 済みの内容だけをパッチファイルに出力
git diff --staged > staged_changes.patch

C. コミット履歴をパッチにする (git format-patch)

git format-patch は、コミットメッセージ、作成者、日付などのコミット情報を含んだパッチを作成します。

# 直近1件のコミットをパッチ化 (0001-commit-message.patch が生成される)
git format-patch -1 HEAD

# main ブランチと現在のブランチの差分コミットをすべてパッチ化
git format-patch main

2. パッチファイルを検証・適用する

ステップ1: 事前チェック（ドライラン）

パッチを実際に適用する前に、エラーや競合（コンフリクト）が発生しないか検証できます。何も出力されなければ安全に適用可能です。

# パッチが正常に適用可能かテスト（ファイルは変更されません）
git apply --check my_feature.patch

# パッチが影響を与えるファイルと行数を確認
git apply --stat my_feature.patch

ステップ2: パッチを適用する (git apply)

# パッチを適用して作業ツリーを変更
git apply my_feature.patch

ステップ3: format-patch 形式のパッチをコミットごと取り込む (git am)

git format-patch で生成されたパッチは、git am コマンドを使うことで、元のコミットメッセージと作成者を保持したままコミットとして適用できます。

# コミット履歴ごとパッチを適用
git am < 0001-feature.patch

競合が発生した場合の対処 (git apply --reject)

コードが一部衝突してパッチが当たらない場合、適用できる部分だけ適用し、衝突した箇所を .rej (reject) ファイルとして書き出すことができます。

git apply --reject my_feature.patch
# 衝突したファイルに対応する .rej ファイルが生成されるので、手動で修正して解消します

6. 作業の一時退避 (git stash) とステージング

作業の途中で「急ぎで別のブランチのバグを直さなければならなくなった」とき、中途半端なコードをコミットすることなく、作業ツリーを一時的にクリーンにする機能が git stash です。

基本の退避と復元

# 現在の変更（未ステージ・ステージ済み）を一時退避
git stash

# メモ（メッセージ）を付けて退避
git stash save "WIP: ユーザー一覧画面の実装途中"

# 新規作成ファイル (Untracked) も含めてすべて退避
git stash -u

部分的に退避する (git stash -p)

git add -p と同様に、対話形式で特定のハンクだけを選んで一時退避させることができます。

git stash -p

退避した作業の確認と復元

# 退避したスタッシュの一覧を表示
git stash list

# スタッシュの中身の差分を確認
git stash show -p stash@{0}

# 最新の退避内容を復元し、スタッシュ一覧から削除する
git stash pop

# 最新の退避内容を復元するが、スタッシュ一覧には残しておく
git stash apply

# 特定のスタッシュを指定して復元
git stash pop stash@{1}

# 不要になったスタッシュを削除
git stash drop stash@{0}

# すべてのスタッシュを一括削除
git stash clear

7. コマンド早見表

用途 コマンド 説明
状態確認 git status -s ステージ・作業ツリー状態を2文字略記で確認
部分ステージ git add -p [ファイル] ハンク（ブロック）単位で選んでステージング
ステージ解除 git restore --staged [ファイル] 作業内容は保持したままステージングを解除
除外反映 git rm --cached [ファイル] 追跡を解除し .gitignore を有効化
未ステージ差分 git diff 作業ツリー vs ステージング領域の差分
ステージ差分 git diff --staged ステージング領域 vs HEAD（次コミット内容）
パッチ作成 git diff > fix.patch 未ステージの差分をパッチファイルに出力
パッチテスト git apply --check fix.patch 適用前にエラーや競合の有無をドライラン確認
パッチ適用 git apply fix.patch パッチの差を作業ツリーに反映
一時退避 git stash -u 未追跡ファイルも含めて作業中の変更を退避
退避復元 git stash pop 退避した最新の作業を復元してスタッシュから削除
