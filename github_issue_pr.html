個人開発からチーム開発まで、GitHubを活用した現代のソフトウェア開発の中心となるのが「Issue（課題・タスク）」と「Pull Request（マージリクエスト・コードレビュー）」です。

本マニュアルでは、タスク起案からブランチ作成、PR提出、レビュー対応、マージ戦略、そしてターミナルから素早く操作できる GitHub CLI (gh) の活用までを体系的に解説します。

1. GitHubフロー（開発サイクル）の全体像

GitHubを用いた標準的な開発サイクルは、以下のステップで一本の線のように進みます。

  1. Issue の作成: バグ報告や新機能要望をIssueとして起案し、要件とゴールを明確化。
  2. 作業ブランチの作成: main からトピックブランチ（例: feat/user-auth）を切って作業。
  3. コミット & リモートへプッシュ: 実装を進め、GitHub上のリモートブランチへ送信。
  4. Pull Request (PR) の作成: 変更内容や背景、関連Issue番号（Closes #12）を記載してPRを作成。
  5. レビュー & 修正コミット: CI（自動テスト）の通過確認と、レビュアーによるコードレビュー・指摘対応。
  6. マージ & Issue自動クローズ: レビュー承認（Approve）後に main へマージし、ブランチを削除。

なぜ直接 main にコミットせず、Issue & PR を使うのか？

  • タスクの見える化: 何を作るのか、なぜ必要なのかが Issue 上で議論・記録され、後から経緯を追跡できます。
  • 品質担保 (レビュー & CI): 自動テストと第三者による確認を経てから本番コード（main）に合流するため、デグレを防げます。
  • 競合の防止: 機能ごとに独立したブランチで作業するため、複数人が同時に別機能を安全に開発できます。

2. Issue (課題管理) の使い方

Issue は、バグ報告・新機能の提案・リファクタリング計画・質問などを記録・追跡するチケット機能です。

Issue に設定できる主要メタデータ

項目 説明 活用のポイント
Assignees そのIssueの担当作業者 誰が作業中かを一目でわかるように設定する
Labels カテゴリや優先度のタグ bug, enhancement, documentation, good first issue など
Milestones リリース時期やイテレーション目標 例: v1.2.0 リリース, 2026-Q3 スプリント
Projects カンバンボード（進行状況） Todo → In Progress → Done の進捗管理

良いIssueを書くためのテンプレート例

## 概要
ユーザーログイン画面にて、Googleアカウント連携ボタンを押した際に403エラーが発生する。

## 再現手順
1. `/login` 画面にアクセス
2. 「Googleでログイン」ボタンをクリック
3. 認証同意画面の直後に403エラー画面が表示される

## 期待される動作
正常にOAuth認証が完了し、ダッシュボード画面 (`/dashboard`) にリダイレクトされること。

## 動作環境 / 関連情報
- OS: macOS 15.0 / Chrome 128
- staging環境で再現確認済み

Issue番号（#番号）の自動リンク:
GitHub上では #123 のようにシャープ記号の後に番号を書くだけで、自動的に対象のIssueやPRへのハイパーリンクになります。コミットメッセージやPR説明欄、チャットで積極的に引用しましょう。

3. Pull Request (PR) の作成と運用

Pull Request (PR) は、「自分が作業したブランチの変更内容を、本体ブランチ（通常は main）に取り込んで（Pull して）ほしい」とリクエストする機能です。

PR作成の流れ

# 1. 最新のmainから作業ブランチを作成
git switch -c feat/login-google

# 2. 開発作業とコミット
git add .
git commit -m "fix: Google OAuth認証のスコープ設定を修正"

# 3. リモートへプッシュ（初めてのブランチの場合は -u origin <ブランチ名>）
git push -u origin feat/login-google

プッシュ後、GitHubのリポジトリトップ画面を開くと、上部に黄色いバーで 「Compare & pull request」 ボタンが表示されます。ここをクリックして作成画面に進みます。

PRの書き方テンプレート（実務推奨）

## 関連するIssue
Closes #42

## 変更内容の概要
Google OAuth認証においてリクエストスコープの指定が不足していたため、403エラーが発生していた不具合を修正しました。

## 実装の詳細・変更点
- `src/auth/google.ts`: 認可スコープに `profile` と `email` を明示
- `tests/auth.test.ts`: 正常系の認可リダイレクト検証テストを追加

## 動作確認手順
1. `npm run dev` でローカル起動
2. `/login` から「Googleでログイン」をクリック
3. テスト用Googleアカウントで認証し、`/dashboard` に遷移することを確認

## レビュアーへの特記事項
UIの変更はなく、内部ロジックのパラメータ修正のみです。

自動クローズキーワード (Closing Keywords):
PRの説明文に Closes #42、Fixes #42、Resolves #42 と記載しておくと、PRがmainにマージされた瞬間に、指定したIssueが自動的にクローズされます。手動でIssueを閉じる手間が省けるため必須のテクニックです。

Draft PR（下書きPR）の活用

PR作成ボタンの右側にある矢印から 「Create Draft Pull Request」 を選択すると、まだレビュー依頼前の「作業中」の状態でPRを作成できます。

  • CI（自動ビルド・テスト）が走るため、プッシュするたびに問題がないかセルフチェックできる
  • 途中の差分をチームメンバーに見せて「この方針で進めてよいか」早期フィードバックをもらえる
  • 誤って途中でマージされるのを防止できる（Draft中はマージボタンが無効化される）

4. コードレビューの流れ

PRが作成されたら、レビュアー（他の開発者）によるコードレビューが行われます。

1. レビュアーの操作 (Files changed タブ)

  • 行コメント: 差分行の左端にある青い + ボタンを押して、特定の行に対して直接コメントを記入できます。
  • Start a review: 複数行にコメントを書き留め、最後にまとめて提出できます。
  • Review changes（レビュー提出）: 画面右上の緑色ボタンから3つの判定を選択して提出します。
    • Comment: 承認・却下の判断は下さず、質問やメモだけを送る
    • Approve: 変更を承認する（マージ可能）
    • Request changes: 修正が必要な点を指摘し、修正が完了するまでマージをブロックする

2. レビュー指摘への対応手順（作成者側）

指摘を受けた場合、PRを新しく作り直す必要はありません。ローカルで修正コミットを行い、同じブランチにプッシュするだけで、PR内の差分が自動更新されます。

# 1. 作業ブランチで指摘箇所を修正
git add src/auth/google.ts
git commit -m "refactor: レビュー指摘に基づきOAuthエラーハンドリングを改善"

# 2. プッシュ（PRが自動的に最新化されます）
git push origin feat/login-google

修正プッシュ後、GitHub上のコメント欄で 「Resolve conversation（会話を解決）」 ボタンを押し、対応完了をレビュアーに報告します。

レビューコメントの慣用句（Tips）

表現 意味 使い方
LGTM Looks Good To Me (問題ありません) Approve時に承認コメントとして添える
nits (nitpick) 些細な指摘（修正しなくても承認可） タイポやインデント等の軽微なアドバイスに付ける
IMO / IMHO In My (Humble) Opinion (私見ですが) 別のアプローチを提案する際の柔らかい言い回し

5. 3つのマージ方法の比較

PRの承認後、GitHubのマージボタンには3つの方式があります。プロジェクトの方針に応じて使い分けます。

マージ方式 コミット履歴の挙動 メリット・デメリット おすすめの用途
Create a merge commit
(通常マージ)		 ブランチ内の全コミットをそのまま残し、マージコミットを1つ作成 + 作業ブランチでの詳細なコミット履歴がすべて残る
− 履歴のグラフが枝分かれして複雑になりやすい		 大規模リリースやGitFlow運用
Squash and merge
(スカッシュマージ)		 ブランチ内の複数のコミットを1つのコミットに圧縮してmainに追加 + mainの履歴が「1 PR = 1 コミット」となり非常に綺麗で見やすい
+ 細かい作業コミットや「typo修正」などが残らない		 一般的なWeb開発・GitHubフロー（最も推奨）
Rebase and merge
(リベースマージ)		 ブランチのコミットをmainの先端に直線状に付け替える（マージコミットなし） + 履歴が完全な一本線になる
− コミットIDがすべて書き換わるため追跡がやや難解		 一本線のフラットな履歴を厳格に維持したい場合

マージ後のローカル同期とブランチ削除:
PRマージ後、GitHub上の「Delete branch」ボタンでリモートブランチを削除し、ローカルPCも最新のmainに同期しておきましょう。

# main に切り替えて最新を取得
git switch main
git pull origin main

# 作業完了したローカルブランチを削除
git branch -d feat/login-google

# リモートで削除されたブランチの追跡情報を整理
git fetch --prune

6. GitHub CLI (gh) によるコマンド操作

GitHub CLI (gh) は、ブラウザを開かずにターミナルから直接IssueやPRの作成、一覧確認、レビュー、マージを実行できる公式ツールです。

初期ログイン

# ブラウザまたはトークンでGitHubに認証ログイン
gh auth login

# ログイン状態の確認
gh auth status

Issue操作コマンド

# 対話式で新しいIssueを作成する（タイトル・本文・ラベル等を入力）
gh issue create

# コマンドライン引数で一発作成
gh issue create --title "ログインボタンのスタイル崩れ" --body "Chromeで幅が狭いときに崩れる" --label "bug"

# 現在開いているIssueの一覧を表示
gh issue list

# 特定のIssueをブラウザで開く
gh issue view 42 --web

Pull Request 操作コマンド

# 現在のブランチから対話式でPRを作成
gh pr create

# コマンドライン引数で一発作成（自動でプッシュも実行されます）
gh pr create --title "fix: Googleログイン認証修正" --body "Closes #42" --base main

# 下書き（Draft）PRを作成
gh pr create --draft

# オープン中のPR一覧を表示
gh pr list

# チームメンバーが作成したPRブランチをローカルにチェックアウトして検証
gh pr checkout 45

# 現在のPRの差分を確認
gh pr diff

# ターミナルからPRをマージ（スカッシュマージしてブランチ削除）
gh pr merge --squash --delete-branch

7. よくあるトラブル & FAQ

Q1. PR上に「This branch has conflicts that must be resolved」と表示された

自分が作業している間に、他の人が main を更新して同じファイルの同じ行を変更したため、競合（コンフリクト）が発生しています。

# 1. ローカルの作業ブランチに切り替える
git switch feat/my-branch

# 2. 最新の main を作業ブランチに取り込む（マージまたはリベース）
git fetch origin
git merge origin/main

# 3. コンフリクトしたファイルをエディタで開き、競合マーカー (<<<<<<<, =======, >>>>>>>) を解消して保存
# 4. 解決したファイルをステージングしてコミット
git add .
git commit -m "fix: mainブランチとの競合を解消"

# 5. プッシュするとPRの競合表示が自動的に解消されます
git push origin feat/my-branch

Q2. レビュー前にPRの対象先（ベースブランチ）を間違えてしまった

PRタイトルの下にある 「Edit」 ボタンを押すと、ベースブランチ（例: develop → main）を後から変更できます。PRを作り直す必要はありません。

Q3. マージした直後に重大なバグが発覚した

マージ済みのPR画面の下部に 「Revert」 ボタンが表示されています。これを押すと、そのPRの変更を完全に打ち消す新しいPRが自動作成されるため、迅速かつ安全にロールバックできます。
